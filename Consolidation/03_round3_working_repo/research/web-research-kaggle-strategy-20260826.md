# Round 3 Research & Strategy — Polymer Property Prediction (7 targets, mean R²)

**Scope:** Kaggle notebook-only competition. One notebook, one end-to-end run (9–12 h session, 2×T4 or P100, ~30 GB RAM, internet OFF during scoring, no pretrained weights/embeddings/external data). Data: 7,409 labeled polymer rows, 995,799 unlabeled polymer SMILES, 5,973,369 unlabeled molecular SMILES. Two judged themes: **explainability** and **SMILES invariance**.

This report synthesizes ~24 web searches plus in-depth reading of the NeurIPS Open Polymer Prediction 2025 winning / silver / 8th-place solutions (the direct predecessor competition: 5 of the same polymer properties, SMILES-only input).

---

## 1. Kaggle notebook limits & self-contained pipeline best practices

- **Session limits.** Interactive kernels are powered off after ~9 hours; GPU sessions have a separate hard time limit and a weekly GPU quota (commonly ~30 h/week on P100/T4). Scoring/submission runs are time-limited too, so everything must fit comfortably inside a single run with headroom. Sources: [9-hour kernel power-off discussion](https://www.kaggle.com/discussions/product-feedback/109715), [notebook duration Q&A](https://www.kaggle.com/discussions/questions-and-answers/694955), [GPU quota after 9 h](https://www.kaggle.com/discussions/product-feedback/402205).
- **Internet is OFF during the scoring run.** You cannot `pip install`, download pretrained weights, or hit any API. "Internet-disabled notebook" also forbids API-based models. Sources: [internet-disabled notebooks](https://www.kaggle.com/discussions/getting-started/511412), [pre-trained models in no-internet competitions](https://www.kaggle.com/discussions/questions-and-answers/473747), [API-based models disallowed error](https://stackoverflow.com/questions/79133027).
- **Offline installs via wheels/datasets.** You can attach a dataset of wheels and `pip install --no-index --find-links`, or build a wheel from a public GitHub repo in advance and upload it. This is *technically* how offline notebooks install extra packages. Sources: [installing custom packages offline](https://dev.to/kito2718/bct2-installing-custom-packages-offline-5cpj), [GitHub project → wheel install](https://zenn.dev/colum2131/scraps/e57cd640246e3a), [gemma4-offline-package dataset](https://www.kaggle.com/datasets/nctuan/gemma4-offline-package).
- **RULE NUANCE — "public code allowed, no pretrained weights/artifacts".** A wheel that contains *only code* (e.g., a plain source library) is arguably "public code." A wheel/checkpoint containing **pretrained weights, learned embeddings, or any model artifact is clearly disallowed.** The safe rule: attach nothing, or attach only pure-source wheels you can justify as code. Do **not** ship ChemBERTa/Mol2vec/polyBERT/ModernBERT/Uni-Mol weights, vocabularies trained on external corpora, or cached embeddings. Everything the model knows must be learned from the 3 in-competition SMILES files. Source for the rule's spirit: [pre-trained models in no-internet competitions](https://www.kaggle.com/discussions/questions-and-answers/473747), [pre-trained models in code competitions](https://www.kaggle.com/discussions/questions-and-answers/240262).
- **Preinstalled stack is generous.** Kaggle's Docker image ships torch, transformers, scikit-learn, XGBoost, LightGBM, CatBoost, SHAP, and **RDKit** (RDKit was added to the official image; DeepChem users note it present by default). So a full Morgan-fingerprint + GBM + SHAP pipeline and a from-scratch PyTorch transformer need **zero** custom installs. Sources: [Kaggle docker-python rdkit issue](https://github.com/Kaggle/docker-python/issues/531), [RDKit as a bundled package/dataset](https://www.kaggle.com/datasets/hamzaabbasai/rdkit-2025-3-6-cp311), [memory allocation in notebooks](https://www.kaggle.com/discussions/questions-and-answers/516616).
- **How winners structure one-run notebooks.** Winners split the run into cached stages: (a) parse/canonicalize SMILES once and cache feature arrays to disk (`np.save`/parquet), (b) build folds once, (c) train each model inside the same fold loop, (d) write OOF predictions to disk, (e) fit the meta-learner on OOF, (f) generate test predictions, (g) write `submission.csv` **last**, and (h) keep a `try/except`/fallback path so a missing optional lib (RDKit/transformers) degrades gracefully rather than killing the run. Sources: [ideal notebook structure discussion](https://www.kaggle.com/discussions/getting-started/301303), [kaggle-format reproducibility skill](https://skills.rest/skill/kaggle-format), [Thiebauts graceful-fallback design](https://github.com/Thiebauts/kaggle-polymer-properties).
- **Practical guardrails:** seed everything; use `set_output(transform="pandas")`; never re-parse SMILES twice; monitor RAM (dense 6M×large embeddings will OOM — keep sparse/float32 and subsample); leave ≥20% time budget slack because scoring containers can be slower than interactive.

## 2. Fast from-scratch self-supervised pretraining on millions of SMILES (single GPU)

The goal is a cheap molecular "embedding" learned **in-notebook** from the ~1M polymer + ~6M molecular SMILES, usable either as tabular features for GBMs or as a frozen/fine-tuned encoder head. Ranked by effort vs. payoff:

- **Character/atom n-gram + TF-IDF (minutes, CPU).** Tokenize SMILES into character n-grams (n=1–8) or regex atom tokens; TF-IDF → sparse matrix → LinearSVR/Ridge/GBM. This is the classic QSAR "N-gram fingerprint" and is extremely cheap and interpretable. Sources: [character n-gram toxicity prediction](https://www.bu.edu.eg/staff/hamadaali14-publications/56401), [SMILES tokenization for substructures](https://avesis.istanbul.edu.tr/yayin/16aa2603-c25e-479c-bba7-ae0e75d25804/).
- **word2vec / fastText on SMILES tokens (minutes, CPU/GPU).** Treat SMILES as sentences (regex tokenization or char-level). fastText/word2vec over ~300M tokens trains in minutes and yields dense vectors that outperform random init on downstream tasks (Mol2vec is exactly this on substructures). Sources: [word2vec & transformer SMILES embeddings](https://www.semanticscholar.org/paper/252ca72a6ca5321c22bd47cd4685b567807249af), [word2vec physical-property deep learning](https://pmc.ncbi.nlm.nih.gov/articles/PMC8912091/), [fastText run-on-GPU](https://github.com/facebookresearch/fastText/issues/451).
- **Moliere / topical skip-gram (optional, minutes).** Moliere builds co-occurrence embeddings of molecules and terms via skip-gram; it is essentially word2vec with a richer context graph. Only worth it if you want a "semantic similarity" angle for the explainability section, not for raw R². Source: [Moliere/molecular skip-gram context](https://pmc.ncbi.nlm.nih.gov/articles/PMC11234358/).
- **Morgan/substructure count matrix + SVD/NMF (minutes-to-1 h, CPU).** Generate count (not binary) Morgan fingerprints (radius 2–3, 1024–2048 bits) or ECFP substructure counts, stack into a sparse matrix, then TruncatedSVD (randomized) or NMF to 128–512 dense features. This is cheap, deterministic, interpretable, and directly matches what the silver solution did (**Morgan 2048 + TruncatedSVD + RDKit descriptors**). Sources: [silver solution README](https://github.com/whyzhow/Kaggle-NeurIPS---Open-Polymer-Prediction-2025-Silver-Algorithm-Overview), [count-based Morgan fingerprint paper](https://pubs-acs-org-443.webvpna.lzu.edu.cn/doi/full/10.1021/acs.est.3c02198).
- **Tiny char/atom-level BERT MLM from scratch (30 min–2 h, single T4).** This is the highest-ceiling *learned* representation and is the right way to replicate "ChemBERTa-style pretraining" **without any pretrained weights**. ChemBERTa-2 is a BERT with masked-language-modeling (MPR) trained on SMILES; MolBERT used ~1.6M SMILES. For one notebook, use a **small** config: 2–4 layers, hidden 128–256, 4 heads, vocab = SMILES token set (30–100 tokens), max seq len 128–256, batch 256–512, 2–5 epochs over a **subsample** (1–2M sequences), mixed precision. Rough T4 estimate: a 2-layer/128-hidden model at seq 128 processes on the order of 5–15k tokens/sec → ~1M short SMILES in well under an hour; scale depth/length down if it is slow. Sources: [ChemBERTa](https://github.com/seyonechithrananda/bert-loves-chemistry), [ChemBERTa-2 paper](https://huggingface.co/buckets/huggingchat/papers-content/tree/2209/2209.01712.md), [MolBERT](https://www.quantumrun.com/consulting/molbert-statistics/), [MolEncoder MLM-for-molecules](https://www.sciencedirect.com/org/science/article/pii/S2635098X25002414).
- **Contrastive self-supervision (MolCLR-style, optional, 1–2 h).** Augment each molecule (atom/node mask, bond/edge perturbation, subgraph sampling, or randomized-SMILES as the "view") and train a contrastive objective. MolCLR shows graph-level contrastive SSL beats supervised-from-scratch on small-data benchmarks. It is more code than MLM but the augmentation itself doubles as your **invariance** story. Source: [MolCLR](https://ar5iv.labs.arxiv.org/html/2102.10056).
- **Recommendation for model size/seq/batch:** prefer *many cheap features* over one big net. 6M molecular SMILES are mostly short (single molecules); 1M polymer SMILES can be longer. Cap seq len at 128 (truncate/pad), use fp16, keep dense embedding dimension ≤256 for the tabular path, and always cache the resulting embeddings to disk before the GBM stage. Do **not** try to fine-tune a 6-layer 768-d transformer on 7.4k labels — that overfits (the winning solution explicitly found larger models failed to help with small fine-tuning data).

## 3. SMILES invariance & augmentation (a scored theme)

- **The invariance problem.** One molecule/polymer has many valid SMILES strings. If the model depends on token order/choice of valid SMILES, its prediction changes when the input is rewritten — the exact robustness flaw Round 3 asks you to address. Sources: [SMILES variation robustness framework](https://www.mendeley.com/catalogue/75704aa6-e65e-3dfb-87ec-c8b38c50ce7b/), [foundation models not enforcing molecular symmetry](https://ar5iv.labs.arxiv.org/html/2510.18900).
- **Canonicalization as the baseline.** `Chem.MolToSmiles(mol, canonical=True, isomericSmiles=True)` gives a deterministic string per molecule — the cheapest way to make train/test consistent and the basis for dedupe/GroupKFold (silver solution canonicalizes first). Source: [silver solution README](https://github.com/whyzhow/Kaggle-NeurIPS---Open-Polymer-Prediction-2025-Silver-Algorithm-Overview).
- **Train-time augmentation (randomized SMILES).** Generate k randomized valid SMILES per molecule (`MolToSmiles(canonical=False, doRandom=True)`), one per epoch or as extra rows. The **winning 2025 solution** generated **10 non-canonical SMILES per molecule (10× data)** for training. Randomized SMILES is a proven regularizer/quality booster in generative and predictive models. Sources: [randomized SMILES improve generative models](https://chemrxiv.org/engage/api-gateway/chemrxiv/assets/orp/resource/item/60c743b14c8919d703ad26a1/original/randomized-smiles-strings-improve-the-quality-of-molecular-generative-models.pdf), [SMILES enumeration as augmentation](https://chao1224.gitbooks.io/running-paper/content/deep-chem/arxiv/smiles-enumeration-as-data-augmentation-for-neural-network-modeling-of-molecules.html), [Maxsmi augmentation "augmentation always helps"](https://hunterheidenreich.com/notes/chemistry/molecular-design/property-prediction/maxsmi-smiles-augmentation-property-prediction/).
- **TEST-TIME AUGMENTATION (TTA) — the highest-impact invariance tactic.** At inference, generate N randomized valid SMILES per test molecule, predict each, and aggregate (median is robust). The **winning solution used 50 predictions per SMILES and aggregated with the median.** This directly lowers variance, averages out representation noise, and *demonstrates* invariance in your notebook. Source: [Xebia analysis of winning approach](https://xebia.com/blog/winning-recipe-for-predicting-polymer-properties/).
- **Consistency / invariance losses.** Add a penalty `λ·mean((f(x) − f(x'))²)` over paired (canonical, randomized) views of the same molecule during training — either as a multi-task loss on a neural encoder or implicitly via augmentation. This is the standard "consistency regularization" from SSL and gives a principled, quantifiable invariance metric to report (e.g., "std of predictions across 20 random SMILES ≤ ε"). Sources: [TTA XAI inconsistencies paper](https://link-hkg.springer.com/article/10.1186/s13321-024-00824-1), [MolCLR augmented-view training](https://ar5iv.labs.arxiv.org/html/2102.10056).
- **Polymer-specific note.** Polymer SMILES often use `*` wildcards for attachment points (BigSMILES-style). Make sure tokenization treats `*` and bracket atoms as single tokens, and test invariance across *different valid polymer representations* (monomer vs. repeating-unit notation), not just atom-order randomization. Sources: [BigSMILES for polymer ML](https://www.cambridge.org/engage/api-gateway/chemrxiv/assets/orp/resource/item/67173b7083f22e4214c58607/original/is-big-smiles-the-friend-of-polymer-machine-learning.pdf), [SMI-TED polymer foundation model](https://ar5iv.labs.arxiv.org/html/2512.11881).
- **Measurable deliverable for the theme:** report the variance/std of predictions across k random SMILES per target, show it shrinks as k grows, and show train-with-augmentation reduces it vs. canonical-only.

## 4. Explainability for regression models in competitions

- **Right tool per model type.** **SHAP TreeExplainer** is exact and near-free for XGBoost/LightGBM/CatBoost/RandomForest; **permutation importance** is model-agnostic and cheap (few seconds per model on 7k rows); **LIME** is the fallback for "local" instances but is slower/noisier; **SHAP KernelExplainer** is too slow for anything but a tiny sample. For a linear model (Ridge/SVR) use coefficient magnitude + standardized coefficients. Sources: [SHAP pypi](https://pypi.org/project/shap/0.22.2/), [choosing an explainer](https://glassalpha.com/guides/how-to/choose-explainer/), [LIME & other interpretation methods](https://yusukehashimotolab.github.io/AI-Knowledge-Notes/knowledge/en/ML/model-interpretability-introduction/chapter3-lime-other-methods.html).
- **Per-target attribution.** This is multi-output regression: run SHAP **separately per target** (7 SHAP plots / 7 feature-importance tables). Report both **global** (mean |SHAP| bar + beeswarm/summary plot) and **local** (force/waterfall plot for 2–3 example polymers, ideally a high- and a low-predicted one). Source: [SHAP global+local explanations](https://aiwiki.ai/wiki/feature_importances).
- **What judges want in "explainability" rounds.** A *story*, not a chart dump: (1) which features matter most and *why it makes chemical sense* (e.g., aromatic ring count ↔ Tg, molecular weight ↔ density), (2) directionality of effects (feature X pushes the target up/down), (3) a local example walk-through, (4) model-level vs. instance-level, and (5) an honest limitations note. Rubrics reward visualization quality and storytelling. Sources: [judging rubric — visualization/storytelling weighting](https://mavmatrix.uta.edu/cgi/viewcontent.cgi?article=1000&context=utadatathon_2025), [XAI choosing guidance](https://www.kaggle.com/discussions/getting-started/581227).
- **Cheap-to-run recipe:** after training the final per-target model, call `shap.TreeExplainer(model).shap_values(X_sample)` on a 500–1000-row sample (full 7.4k is fine for trees), then `shap.summary_plot` + `shap.plots.bar` + one `shap.plots.waterfall`. Total runtime seconds. Keep the explainability section deterministic (fixed seed) so it reproduces.
- **Connect explainability to the other theme:** show SHAP on a model whose features are SMILES-derived (atom counts, substructure bits, n-gram TF-IDF terms) — these are human-readable, which makes the explanation chemically interpretable, unlike raw token embeddings.

## 5. Squeezing R² on small tabular data (7.4k labeled rows)

- **Grouped CV is mandatory and non-negotiable.** Use `GroupKFold` on **canonical SMILES** (or on the polymer identity) so no polymer leaks across folds; this was explicitly flagged in the silver solution to prevent molecule-level leakage. A plain random KFold will inflate your CV and let you ship a model that underperforms on the private split. Source: [silver solution GroupKFold](https://github.com/whyzhow/Kaggle-NeurIPS---Open-Polymer-Prediction-2025-Silver-Algorithm-Overview).
- **Target encoding risks.** Target encoding on high-cardinality categoricals (rare substructures, SMILES prefixes) leaks if computed on the full training set. Use **out-of-fold target encoding** (encode each fold using only the other folds' targets) and add smoothing/regularization; never encode the test set with test labels (you don't have them) or with in-fold train labels. Sources: [target encoding leakage](https://stats.stackexchange.com/questions/567095/target-encoding-in-test-data-and-target-leakage/567124), [target encoding "isn't it leakage"](https://www.kaggle.com/discussions/getting-started/140588).
- **Stacking/blending discipline.** Compute **out-of-fold (OOF) predictions** for every base model, then train a simple meta-learner (Ridge/ElasticNet, or LightGBM with tiny depth) on the OOF stack. The silver solution used exactly this: CatBoost + XGBoost bases → **Ridge meta-learner** (optional Optuna weights). Sources: [silver solution OOF stacking](https://github.com/whyzhow/Kaggle-NeurIPS---Open-Polymer-Prediction-2025-Silver-Algorithm-Overview), [Kaggle ensembling guide](https://web.archive.org/web/20160304031055/http://mlwave.com/kaggle-ensembling-guide/), [stacking & blending](https://engineersofai.com/docs/ml/tree-models/stacking-and-blending).
- **Multi-seed bagging.** Average the same model over 5–10 seeds (and/or subsample rows/columns) for a free variance reduction; combine with TTA (randomized SMILES × seeds × folds → median). Bagging is a cheap, reliable R² bump on small data.
- **Property-specific models.** Do **not** force one model for all 7 targets. The winning solution built **property-specific** models and the Thiebauts repo showed different targets need different configs (Tg wanted depth limits; FFV didn't). Small-data targets (few hundred–1k rows) need heavy regularization/shallow trees, larger targets can go deeper. Sources: [Xebia winning analysis](https://xebia.com/blog/winning-recipe-for-predicting-polymer-properties/), [Thiebauts key findings](https://github.com/Thiebauts/kaggle-polymer-properties).
- **TTA & calibration.** Aggregate randomized-SMILES predictions with the **median** (robust to outlier representations). For R², median/mean over TTA helps only if representations actually vary — which they do for SMILES. Optional: an isotonic/linear calibration on OOF per target if you see systematic bias (the winner used isotonic regression to *rescale labels*, and a simple `Tg += std·0.5644` to fix a distribution shift).
- **Leaderboard-overfitting pitfalls (documented in this exact family).** In the predecessor competition the **public LB used ~8% of test data** and the private used ~92%; a top-10 team described losing the competition by swapping to a "worse model" on the last day because it looked better on the small public split. Lesson: trust **GroupKFold CV**, not the public LB; don't chase the LB with last-minute model swaps; expect **distribution shift** between train and the hidden test (the winner found a real Tg shift and corrected it). Sources: [Gaurav solution & final-day mistake](https://github.com/Gaurav-Kushwaha-1225/NeurIPS-Open-Polymer-Prediction-2025), [8th place no-Tg-post-processing writeup](https://www.kaggle.com/competitions/neurips-open-polymer-prediction-2025/writeups/8th-place-solution-no-tg-post-processing).
- **Near-duplicate handling.** Compute Tanimoto similarity between train and test (or intra-train) molecules and drop train rows that are near-identical (winner used >0.99 on train-test monomer pairs) to avoid leakage through duplicate polymers. Source: [Xebia winning analysis](https://xebia.com/blog/winning-recipe-for-predicting-polymer-properties/).

## 6. Prior art: molecular/property Kaggle & polymer prediction competitions

- **NeurIPS Open Polymer Prediction 2025** is the direct ancestor (5 polymer properties from SMILES; this Round 3 = 7 properties, mean R²). Its solutions are the single most transferable resource:
  - **Winning (James Day):** property-specific ensembles of **ModernBERT (general-purpose BERT beat ChemBERTa/polyBERT)**, **AutoGluon** (tabular), and **Uni-Mol-2-84M** (3D); polyBERT embeddings kept as tabular features; **randomized SMILES 10× train / 50× TTA with median**; Tg shift post-processing (`Tg += std·0.5644`); isotonic label rescaling; error-based filtering + Optuna per-dataset sample weights; Tanimoto near-dup removal; a pairwise-comparison pretraining stage; differentiated learning rates (backbone 10× lower than head). Source: [Xebia analysis of the winning approach](https://xebia.com/blog/winning-recipe-for-predicting-polymer-properties/).
  - **Silver (whyzhow):** SMILES canonicalization → Morgan 2048 + TruncatedSVD + RDKit descriptors → **GroupKFold on canonical SMILES** → CatBoost/XGBoost → **OOF Ridge stacking** (+ optional GNN, Optuna weights). Minimal, reproducible, and almost entirely rules-compliant as-is. Source: [silver solution](https://github.com/whyzhow/Kaggle-NeurIPS---Open-Polymer-Prediction-2025-Silver-Algorithm-Overview).
  - **Thiebauts:** baseline **Random Forest + 13 hand-crafted SMILES features** already hits non-trivial R² (Tg 0.535, FFV 0.667, Tc 0.832, density 0.580, Rg 0.490); Optuna > GridSearchCV (13.6% Tc gain); dataset size is the bottleneck for small targets. Source: [Thiebauts repo](https://github.com/Thiebauts/kaggle-polymer-properties).
  - **Gaurav (top-10):** property-specific GNN ensemble (custom GNN for Rg/density, molecular-fingerprint GNN for FFV/Tg, data-augmentation GNN for Tc); 5-fold CV; MAE loss; early stopping; and the cautionary public/private overfit tale. Source: [Gaurav solution](https://github.com/Gaurav-Kushwaha-1225/NeurIPS-Open-Polymer-Prediction-2025).
  - **8th place:** solid tabular/GNN solution that deliberately skipped Tg post-processing. Source: [8th place writeup](https://www.kaggle.com/competitions/neurips-open-polymer-prediction-2025/writeups/8th-place-solution-no-tg-post-processing).
- **Other molecular-property Kaggle kernels** converge on the same shape: `SMILES → RDKit → LGBM` is a well-known strong baseline. Source: [SMILES→RDKit→LGBM kernel](https://www.kaggle.com/code/richolson/smiles-rdkit-lgbm-ftw).
- **Directly transferable rule-compliant insight:** the winning recipe's *mechanisms* (TTA, GroupKFold, OOF stacking, property-specific models, distribution-shift correction, dedup) transfer 1:1; only its *ingredients* (pretrained ModernBERT/Uni-Mol, external RadonPy/PI1M/MD data) are off-limits here and must be replaced with from-scratch in-notebook equivalents.

## Implications for Round 3 plan (ranked by expected impact)

**Rules-compliant means:** no pretrained weights/embeddings/external data; no downloaded checkpoints; pure code is OK; RDKit/torch/transformers/sklearn/XGBoost/LightGBM/CatBoost/SHAP are preinstalled. Everything below is trainable in-notebook.

1. **Grouped CV + OOF stacking of GBM on rich SMILES features (foundation, do first).** Canonicalize all SMILES once; build Morgan(count 2048) + TruncatedSVD + RDKit descriptors + char n-gram TF-IDF; `GroupKFold` on canonical SMILES; CatBoost/XGBoost/LightGBM per target; OOF → Ridge/ElasticNet meta-learner. This mirrors the silver solution and is near-guaranteed to be solid and interpretable. *(Sources: silver README, Thiebauts.)*
2. **Randomized-SMILES TTA with median aggregation (biggest invariance + variance win).** Train with k randomized SMILES per row (augmentation) and, at test time, predict N randomized valid SMILES per polymer and take the median. This is the winning solution's highest-leverage, fully-rules-compliant move, and it is *also* the empirical proof for the invariance theme. *(Source: Xebia.)*
3. **From-scratch tiny char/atom BERT MLM on the unlabeled SMILES (the "foundation" play without pretrained weights).** Pretrain a 2–4 layer / 128–256 hidden BERT via masked-SMILES-token modeling on 1–2M (subsample of the ~7M) SMILES for ~30–90 min on T4; pool the last hidden state into a 128–256-d embedding and add it to the tabular feature set (or a light fine-tune head). This substitutes for the forbidden ChemBERTa/ModernBERT embeddings. *(Sources: ChemBERTa-2, MolBERT.)*
4. **Per-target model selection with regularization tuned to data size.** Small targets → shallow trees/strong reg/early stopping; large targets → deeper. Optionally add the pairwise-comparison pretraining trick (predict which of two polymers has the higher property) as a cheap SSL signal on unlabeled pairs. *(Sources: Xebia, Thiebauts, Gaurav.)*
5. **Multi-seed bagging + fold-consistent averaging.** Average 5–10 seeds of the top models; combine with TTA; report CV (GroupKFold) as the truth, never the public LB.
6. **Explainability section (theme 1).** Per-target `TreeExplainer` SHAP: global beeswarm + bar, one force/waterfall per target, plus a "chemical sense" narrative (why MW/substructure bits drive each property). Quantify invariance (theme 2): std of predictions across 20 random SMILES per polymer, and show it drops with TTA and with augmentation-trained models. Both sections run in seconds and double as judging deliverables.
7. **Distribution-shift / bias guardrails.** Check each target for train-vs-test distribution shift (as the winner found for Tg) and, if present, apply a simple OOF-derived shift correction; use Tanimoto dedup (drop train rows >0.99 similar to test / near-duplicates) to prevent leakage. *(Sources: Xebia, Gaurav.)*
8. **Avoid the traps.** Do not attach any pretrained weights/wheels-of-embeddings (violates "no artifacts"); do not rely on internet at scoring time; cache every heavy feature to disk; keep RAM in check (sparse/float32, subsample the 6M molecular set for anything dense); leave a time buffer.
